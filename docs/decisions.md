## D-001 修改婚礼日期后，已有任务截止日期如何处理

- **日期与状态**：2026-10-01 提出；2026-10-02 已确认。
- **关联**：REQ-004 AC-011 / AC-041；REQ-005 AC-012 / AC-013 / AC-015；API-009、API-010、API-012。
- **问题与体验影响**：建项后用户可以改档案里的婚礼日期。倒计时和「当前阶段」必须跟新婚礼日走。任务建议截止日期是否跟着改，原先未写。

| 可选方案 | 用户体验与代价 | 技术依据或待验证项 |
| --- | --- | --- |
| A. 只改档案，已有截止日期全部不动 | 倒计时和当前阶段立刻变；任务日期可能和新年礼日对不上，用户要自己改 | 实现最简单；无额外字段 |
| B. 没改过截止日期的任务按新婚礼日重算；用户改过的保留 | 大多数模板任务自动对齐；手动改过的日期不被覆盖 | 任务需记录「截止日期是否被用户改过」 |
| C. 全部任务截止日期按新婚礼日重算 | 日期一定对齐，但用户改过的日期会丢失 | 破坏已有编辑，恢复成本高 |

- **建议及理由**：建议 **B**。改婚礼日通常是整体推迟或提前，未改过的建议日期应当重算；已经手改的视为用户决定，应保留。
- **最终选择与确认依据**：选择 **B**。2026-10-02 用户原话「全部按建议」。
- **落地与验收**：PRD AC-041；tech-spec API-009 / API-012 与 `due_date_customized`。验证：婚礼日 2027-10-20 改为 2027-11-20 后，未改过的备婚启动截止日变为 2027-05-20；用户改过的那一条保持原值；倒计时和当前阶段按 2027-11-20。测试尚未执行。
- **复议条件**：若 1.0 明确禁止改婚礼日，本条可关闭。

## D-003 找回密码的短信通道，以及手机号是否全站唯一

- **日期与状态**：2026-10-01 提出；2026-10-02 已确认。
- **关联**：REQ-001 AC-001 / AC-002 / AC-043；REQ-003 AC-007 / AC-008；API-001、API-003、API-004；外部接口 EXT-001。
- **问题与体验影响**：找回密码必须把验证码发到注册手机。这决定：1）重复手机号能不能注册；2）没配短信账号时用户能不能找回密码；3）是否产生短信费用。

| 可选方案 | 用户体验与代价 | 技术依据或待验证项 |
| --- | --- | --- |
| A. 手机号全站唯一；开发默认 Mock（验证码只写服务端日志，页面不展示）；生产用阿里云 `SendSms` | 同一手机不能注册第二个账号；本地开发无需短信费；上线前要有已审核签名和模板，按条计费 | 阿里云 SendSms 官方文档：<https://help.aliyun.com/zh/sms/developer-reference/api-dysmsapi-2017-05-25-sendsms>。国内短信不幂等，失败后不能盲目重试。无密钥时不影响注册/登录/三个模块 |
| B. 从开发起就走阿里云，无密钥则找回密码直接失败 | 本地联调找回密码必须有真实账号和审核通过的模板 | 签名/模板审核周期待用户侧完成，本阶段未实测发送 |
| C. 允许同一手机号注册多个账号 | 找回密码无法判断改哪一个账号，通道不可用 | 与 REQ-003 冲突 |

- **建议及理由**：建议 **A**。手机号唯一才能把验证码对应到唯一账号。开发用 Mock 不阻塞其他功能；生产再接阿里云。页面不回显验证码，避免公开站点泄露。
- **最终选择与确认依据**：选择 **A**。2026-10-02 用户原话「全部按建议」。
- **落地与验收**：PRD AC-043（重复手机号不能再注册）；tech-spec API-001 / API-003 / EXT-001 与 `sms_mode`。Mock 模式下日志出现验证码且页面不展示、短信未真实发出；生产模式需真实手机收到验证码。测试尚未执行。缺少阿里云密钥只阻碍找回密码真实验证，不阻碍其他模块。
- **复议条件**：用户指定其他国内短信商时，替换 EXT-001，不得沿用本记录中的阿里云字段。
- **复议**：2026-10-06 用户说明自己是个人开发者，阿里云要求走号码认证的短信认证。EXT-001 改为 `SendSmsVerifyCode`（`dypnsapi.aliyuncs.com`），使用赠送签名和赠送模板。验证码仍由本服务生成并在本地校验；短信正文同时带 `code` 和 `min`。Mock、页面不回显验证码、缺密钥不影响注册登录，这些不变。

## D-005 选中 DeepSeek Pro 时发送图片

- **日期与状态**：2026-10-02 提出；2026-10-02 已确认。
- **关联**：REQ-014 AC-062 / AC-067 / AC-087；REQ-016；API-033、API-035、API-036、API-040；EXT-002。
- **问题与体验影响**：已确认用户可以发图片，也可以在输入框旁切换 Deepseek 模型，选择跟当前对话走。2026-10-02 官方定价页：`deepseek-flash` 支持 Vision；`deepseek-v4-pro` 标注 Vision 不支持。非视觉模型收到图片会 400。若悄悄丢掉图片，等于改掉「用户可以发图片」。

| 可选方案 | 用户体验与代价 | 技术依据或待验证项 |
| --- | --- | --- |
| A. 下拉只保留 Flash | 发图始终能被模型看见；用户不能再换 Pro，和「可切换模型」几乎只剩一个选项 | 定价页 Vision 仅 Flash。实现最简单 |
| B. Flash 与 Pro 都可选。选 Pro 时不能把图片加入待发送（入口不可用或点了提示改回 Flash）。Flash 下发图照常 | 发图能力仍在，只是绑在 Flash。想用 Pro 时这一轮只能发文字。等待与费用：Pro 更贵、无图 | 默认模型已定为 Flash。不修改「可以发图片」 |
| C. 选 Pro 仍可点发送带图；这一轮自动改用 Flash 看图，下拉显示仍是 Pro | 图一定能被看见，但用户以为在用 Pro | 和「选择跟当前对话走」不一致，容易误解 |
| D. 选 Pro 时把图发出去但不给模型看（或让请求失败后当普通失败） | 用户以为模型看见了图，回答对不上；或发不出却无明确原因 | 等于削弱已确认的发图。不建议 |

- **建议及理由**：建议 **B**。默认 Flash，发图走官方支持的视觉模型。需要 Pro 时这一轮不带图，并说清当前模型看不了图片。不采用 D。
- **最终选择与确认依据**：选择 **B**。2026-10-02 用户原话「1）B」。
- **落地与验收**：PRD AC-087；tech-spec API-035 / API-036 / API-040 与 §五。验证：Flash 下可发图；Pro 下加入图片不进入待发送，看到「当前模型看不了图片，请改用 Flash 后再发送图片。」；不自动改用 Flash。测试尚未执行。
- **复议条件**：若 Deepseek 日后为 Pro 开放 Vision，可重议是否允许 Pro 发图。

## D-006 调用 Deepseek 时是否开启思考（页面仍不展示思考）

- **日期与状态**：2026-10-02 提出；2026-10-02 已确认。
- **关联**：REQ-014 AC-064 / AC-067；REQ-016 AC-084；API-035、API-036、API-038、API-039、API-040；EXT-002。
- **问题与体验影响**：已确认对话里只显示最终回答、不显示思考过程。官方思考模式默认开启（`thinking.type=enabled`，`reasoning_effort` 默认 `high`）。思考内容走 `reasoning_content`，最终回答走 `content`。若开启思考：最终文字出现前可能长时间空白（思考不展示），更容易在「还没有任何文字」时点停止；token 与费用更高，复杂题可能更稳。若关闭：文字更快开始出现，费用更低，部分取舍题可能稍弱。超时 90 秒更常发生在开启思考时。

| 可选方案 | 用户体验与代价 | 技术依据或待验证项 |
| --- | --- | --- |
| A. 关闭思考（`thinking.type=disabled` 或 `reasoning_effort=none`） | 回复更快开始往外流；平台费用更低；备婚常识题通常够用 | [Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode)；非思考时 `max_tokens` 默认 8K |
| B. 开启思考，只把 `content` 给用户 | 质量可能更好；开口前可能空等较久；费用更高（输出含推理 token） | 官方默认；思考时默认 `max_tokens` 64K。本产品仍截到配置的 8192 最终输出预算 |
| C. `reasoning_effort=low` | 介于 A、B：等待和费用低于 high，可能仍有一段空白 | 文档：low 会开启思考 |

- **建议及理由**：建议 **A**。1.0 是备婚问答不是解题；已要求不展示思考。关闭后流式体验与 AC-064 的「逐步出现」更一致，也降低超时和费用。需要时再开 B。
- **最终选择与确认依据**：选择 **A**。2026-10-02 用户原话「2）A」。
- **落地与验收**：tech-spec EXT-002 请求体 `thinking.type=disabled` 且 `reasoning_effort=none`；§七配置默认值。页面仍只显示最终回答，不新增产品文案。测试尚未执行。
- **复议条件**：若真实联调关闭思考后范围拒绝、表格或「远低于」句经常不合格，可改为 B 并保持不展示思考。
